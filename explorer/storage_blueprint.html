O&G Value Chain Knowledge Graph · Architecture sheet A-02 · Prototype v0.2 design

One model, three stores

OWL holds the meaning, the triplestore reasons, validates and exchanges, and the property graph runs the day-to-day queries. Every entity keeps one IRI in all three, so a fact about E-101B means the same thing wherever it's read.

OWL · SHACL · SKOS (git) Triplestore (RDF) Property graph runtime (LPG) Inferred / hypothesis

Who writes where, and what flows between the stores

Each kind of data has exactly one writer. Source systems write instances into the property graph. The ontology is authored only in git. The triplestore's reasoning returns to the property graph only as hypothesis edges.

One entity, three forms: E-101B overhead condenser

The same condenser from the prototype, written three ways. OWL says what a shell-and-tube exchanger is. The triplestore holds E-101B as subject–predicate–object statements. The property graph holds it as a node with properties, linked to its facts and failures.

Four jobs the triplestore does, on our prototype data

Each example shows the question, the mechanism and the query, plus what it returns on the Refinery Alpha and Beta demo data.

“List every heat exchanger at Refinery Alpha.”

No statement says E-101B is a heat exchanger, or that it's part of the site. The ontology supplies both: the class chain gives Type DNA and the part-of chain gives Lineage DNA.

Returns: E-101AE-101BE-301E-401A and E-601 are heat exchangers too, but at Beta, so they're excluded.
SPARQL · runs on any SPARQL 1.1 store
SELECT ?eq WHERE {
  ?eq a/rdfs:subClassOf* ogkg:HeatExchanger ;
      ogkg:partOf+ alpha:SITE-ALPHA .
}
With an OWL-RL reasoner switched on
SELECT ?eq WHERE {
  ?eq a ogkg:HeatExchanger ;
      ogkg:partOf alpha:SITE-ALPHA .
}

The property graph can answer this too, but the query has to spell out the paths ([:IS_A*], [:PART_OF*]). In the triplestore the meaning is built into the ontology.

“Which equipment is at risk when we run high-salt crude?”

Rule R-07 joins crude chemistry, unit topology and tube metallurgy. What it produces is a hypothesis, not a fact.

Hypothesis lifecycle
proposed · 0.8→corrosion engineer reviews→validatedorrejected

Once validated, the turnaround-scope insight picks it up automatically. Salt threshold and rule are illustrative.

SPARQL CONSTRUCT · rule R-07
CONSTRUCT { ?eq ogkg:atRiskOf pattern:OverheadChlorideCorrosion . }
WHERE {
  ?camp ogkg:ofGrade ?g ; ogkg:processedIn ?unit .
  ?g    ogkg:saltContent ?salt .  FILTER(?salt > 20)
  ?sec  ogkg:partOf ?unit ; a ogkg:OverheadSystem .
  ?eq   ogkg:partOf ?sec ;
        ogkg:tubeMetallurgy vocab:CarbonSteel .
}
Written back to the property graph as a hypothesis edge
MATCH (e:Equipment {id:'E-101B'}),
      (p:ProblemPattern {id:'OverheadChlorideCorrosion'})
MERGE (e)-[h:AT_RISK_OF]->(p)
SET h.status = 'proposed', h.confidence = 0.8,
    h.inferred_by = 'R-07 (triplestore)',
    h.run_id = '2026-09-30T02:00',
    h.evidence = ['FL-002','IOW-002']
“Is every pump complete enough for AI to reason about?”

A SHACL shape states what a complete pump record must contain. Run against the prototype, it finds a gap that was already there.

Why it matters: P-103 silently drops out of the bad-actor analysis. Without SHACL, an AI would give an incomplete fleet answer and nothing would flag it.
SHACL shape
ogkg:PumpShape a sh:NodeShape ;
  sh:targetClass ogkg:Pump ;
  sh:property [ sh:path ogkg:model ;    sh:minCount 1 ] ;
  sh:property [ sh:path ogkg:sealPlan ; sh:minCount 1 ] ;
  sh:property [ sh:path ogkg:serviceTemperature ;
                sh:minCount 1 ; sh:datatype xsd:decimal ] .
Validation report (excerpt)
[ a sh:ValidationResult ;
  sh:focusNode    alpha:P-103 ;
  sh:resultPath   ogkg:model ;
  sh:resultSeverity sh:Violation ;
  sh:resultMessage "Less than 1 value" ] .

The same shapes also gate incoming data. Nothing is promoted to the property graph until it conforms.

Three rules that keep the stores in step

RULE 1

One writer per kind of data

Source systems write to the property graph. The ontology is written only in git. Rules write only hypothesis edges.

RULE 2

Mirror selectively

Entities, relations and facts go to the triplestore. Time series, raw logs and document text do not.

RULE 3

Recompute inferences, never edit them

Drop the inferred graph and rerun the rules. Stable IRIs make that safe, and every hypothesis edge records the run that made it.
